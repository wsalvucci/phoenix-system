# Testing

Phoenix has three layers of automated tests. Two of them run against a **local** Supabase stack that is built
from `supabase/migrations/` and seeded with obviously fictional data, so they exercise real sessions, row level
security and the SQL functions.

| Layer | Command | What it covers | Needs Docker |
|---|---|---|---|
| Unit | `npm run test:unit` | Pure TypeScript: point math, link codes, display access, filtering | No |
| Database | `npm run test:db` | pgTAP (`supabase/tests/database`) and role-level API checks (`tests/rls`) | Yes |
| End to end | `npm run test:e2e` | Playwright, one browser session per role, against the running app | Yes |
| All three | `npm run test:all` | In that order | Yes |

CI (`.github/workflows/test.yml`) runs all of them on every pull request and on `master`.

## Safety: this repository's Supabase CLI is linked to production

Treat the CLI as linked to the live project (on the main checkout it is). Everything here is built so that nothing can reach it, and you must
keep it that way:

- Only run `supabase start`, `supabase stop`, `supabase status`, `supabase test db`, and the `npm run test:*` scripts.
- Never run `supabase db push`, `migration repair`, `link`, `db pull`, or any command with `--linked`, `--db-url`
  or `--project-ref`.
- `supabase db reset` is local by default, but use `npm run test:db:reset`: it checks that the target is on
  `127.0.0.1` and refuses otherwise.
- Test keys live in `.env.test.local` (gitignored, generated by `npm run test:env` from `supabase status`). The
  production `.env.local` is never read. `playwright.config.ts` and `tests/helpers/localStack.ts` refuse to run
  unless `NEXT_PUBLIC_SUPABASE_URL` is `127.0.0.1` or `localhost`, and the dev server is started with the test
  environment passed explicitly, which wins over any `.env.local`.
- The seed creates accounts with a known password. It only ever runs on the local stack.

## First run

```bash
docker info                  # Docker Desktop must be running
npm ci
npx playwright install chromium

supabase start               # local stack, ports 544xx; first run pulls images (a few minutes)
supabase status              # confirm the URLs are http://127.0.0.1:544xx
npm run test:db:reset        # replay migrations + load supabase/seed.sql, then write .env.test.local
npm run test:all
```

Day to day: `supabase start` once, then `npm run test:db`, `npm run test:e2e`. Run `npm run test:db:reset` whenever
a migration or the seed changes, or after a run that was killed half way. `supabase stop` when finished.

The local ports are 54421 (API), 54422 (database) and 544xx for the rest, not Supabase's default 543xx, so the stack
can run beside another project's. The stack runs only Postgres, Auth, REST and Realtime. Studio, Inbucket (mail),
Storage and Edge Functions are off in `supabase/config.toml`.

`npm run test:e2e` starts `next dev` on port 3100 itself (`E2E_PORT` to change) and refuses to reuse a server that
is already listening there. To test the production build: `npm run build` with the variables from
`.env.test.local` exported, then `E2E_SERVER=start npm run test:e2e` (this is what CI does).

## Database tests

`npm run test:db` = `supabase test db` (pgTAP) then `vitest -c vitest.rls.config.ts`.

**pgTAP** (`supabase/tests/database/*.test.sql`), each file in a rolled-back transaction:

| File | Covers |
|---|---|
| `01_grants` | anon executes nothing; authenticated executes exactly the 13 student-facing RPCs; server-only tables have no grants; RLS on every table; `search_path` pinned |
| `02_publication_cut` | `publication_cut` against the table in `DATA_DISCLOSURE.md` section 8.4; `display_cut` shape (no id, no count), ties shrink, zero and negative never published, per-cohort cuts, every refusal looks like "no rows", synthetic cohorts of 0 to 120 |
| `03_points_to_next_rank` | gaps only, floors (grade, group and point group appear at 10 participants), who may ask |
| `04_link_codes` | `redeem_link_code` uniform failure, 5 per user per hour, 20 per client key, 24 hour purge, normalisation; `preview_link_code` |
| `05_display_devices` | pairing, single-use claim, who may approve, lapse when the pairer stops being staff, reconfirm, revoke |
| `06_share_withdrawal` | editing a shared score un-shares it, one notice, read once, only for the owner |
| `07_leader_letters` | letter thresholds, rule L8 (6 members, 0 or 3 or more at D and at E, more than half took part) on synthetic data |

Tests that need exact cohort sizes build a throwaway school inside the transaction; nothing persists.

**Role-level API checks** (`tests/rls/rls.test.ts`) sign in with the anon key exactly as the app's cookie client
does and assert what each role can call and read through PostgREST: anon and every authenticated role are refused
the server-only RPCs and tables, cannot write scores or change other users' rows, never read the other school's
rows, and the student RPCs return no other student's id and no counts.

## End-to-end tests

`tests/e2e`, run with one worker in file order because they share one database.

| File | Covers |
|---|---|
| `auth.setup.ts` | Signs in once per role through the real form and saves the session to `tests/e2e/.auth/` |
| `auth.spec.ts` | Sign-in, bad password, safe redirects, logout, signed-out visitors see no data |
| `roles.spec.ts` | Admin, teacher, student, leader, TA, zero-point student, parent, no-role account: main screens load, show their own data, raise no 5xx, page errors or database error text |
| `forbidden.spec.ts` | Cross-role and cross-school refusals: student to admin/teacher/dashboards, parent to another child, teacher to another teacher's group, admin of school 2 to school 1 |
| `dashboards.spec.ts` | Every `/dashboard/*` board, as admin and teacher: names only from `display_cut` (compared to the database), no counts or denominators, no ids in server responses |
| `display.spec.ts` | Kiosk pairing end to end, bound to its school, cannot reach staff pages, revoke, lapse when the pairer leaves, reconfirm, tampered cookie |
| `linking.spec.ts` | Uniform failure, rate limit, successful student, parent and teacher links (data restored afterwards) |

Failures keep a screenshot and trace in `test-results/` (`npx playwright show-trace <trace.zip>`).

## Known findings

These are real behaviors the suite found. They are recorded as expected-failure markers, so they do not fail the
run, and they will tell you when they are fixed.

1. **RLS leaves signed-in users with no readable rows (backend).** Only 9 policies exist, none lets a teacher, student
   or parent read `user`, `student_point`, `point_event`, `student_group`, `school` and most other tables, and the
   admin policies on `student` and others subquery tables that have no policy of their own, so they match nothing.
   Anything that reads through the anon-key cookie client therefore gets zero rows today. Every screen the e2e suite opens still works,
   because those paths authorize the caller and then read with the service client. Expected-failure markers in
   `tests/rls/rls.test.ts` ("KNOWN GAPS") show the intended behavior. Any new code that reads through the cookie
   client will return empty data until policies exist.
2. **anon holds INSERT/UPDATE/DELETE grants on `student_point`, `point_event`, `user`, `student` (backend).** Supabase
   default privileges; RLS is the only guard. pgTAP TODO in `01_grants`.
3. **Home page raises server errors for every role the user does not have (frontend).** `HomeRoles` calls the admin,
   teacher, student and parent loaders with `Promise.allSettled`, and the ones that do not apply throw, so each home
   visit logs two or more 500s from server actions. The e2e home check tolerates this.
4. **Staff-only pages show "Loading…" forever to the wrong role (frontend).** `/admin` and `/teacher` as a student,
   parent or the wrong staff role stay on a spinner (the server action throws) instead of redirecting. No data
   leaks; the check is that none is shown.
5. **A negative score renders as "+-5" on the student page (frontend).**

## Adding tests

- SQL behavior: add `supabase/tests/database/NN_name.test.sql` (begin; plan; ...; finish; rollback). Prefer a
  synthetic school built inside the test over editing the seed.
- Role or RLS behavior: `tests/rls/*.test.ts` using `signedIn(role)` from `tests/helpers/localStack.ts`.
- A screen or flow: `tests/e2e/*.spec.ts`; use `authFile(role)` for a stored session and `watchProblems` /
  `settle` from `tests/e2e/helpers.ts`. A test that changes data must restore it.
- Changing the seed changes expectations in all three layers: search for the student names and totals above.

## Troubleshooting

- `Cannot connect to the Docker daemon`: start Docker Desktop.
- `port is already allocated`: another stack is using the port. This repo uses 544xx; check `docker ps`.
- Do not `supabase stop` another project's stack to free a port; change ours in `supabase/config.toml` instead.
- `Refusing to run e2e`: `.env.test.local` is missing or not local; run `npm run test:env`.
- `webServer ... already used`: something is listening on 3100; stop it or set `E2E_PORT`.
- Flaky first e2e test with `next dev`: the first request compiles the page. The timeouts allow for it.
